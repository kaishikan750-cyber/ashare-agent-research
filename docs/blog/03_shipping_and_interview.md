# 从能跑到能交付：Agent 项目的 API、MCP、Docker 和 CI

一个实习作品最好让面试官能复现。我的第三阶段交付包含启动器、锁定依赖、容器定义、CI、博客、字幕演示和研究结果，而不只是架构图。

## 先让第一次运行简单

`python start_stage3.py` 自动创建独立 `.venv-stage3`，安装 `requirements-stage3-lock.txt` 并做 pip check，然后启动单进程 FastAPI。无需激活 PowerShell 环境。离线模式没有模型 API 成本，人工行情随包提供；真实行情不会自动下载或被打进交付包。

我实际从空环境运行了启动器并生成研究报告，也在该环境跑了项目测试。检查发现新版 NumPy 要求 Python 3.12+，于是锁文件用环境标记为 Python 3.11 单独选择 2.3.3。依赖锁定不是一份 freeze 粘贴结束，还要看声明的运行版本是否真的兼容。

## FastAPI 和前端的职责

POST `/api/experiments` 返回 202；前端根据 ID 轮询状态。任务复制 CSV、执行 LangGraph、存工具事件、生成报告。第三阶段用可选 study 配置扩展旧请求，保持没有 study 的旧流程。页面展示基本回测、样本外股票池表、策略/基准曲线、每折日期和参数、敏感性网格。报告下载与历史实验重载都有自动浏览器验证。

当前 SQLite + 两线程是本地研究原型，不支持多个 uvicorn worker 共同协调队列。模型失败会保留已完成的计算结果并明确回退来源；关键计算失败则整个任务失败，不能默默返回“没信号”。这些边界比把所有错误都藏成成功更有价值。

## MCP 提供另一个入口

MCP stdio 服务复用 ResearchTools，并新增 run_validation_study。客户端通过 JSON-RPC 发现工具和调用；它可以不启动 FastAPI。测试实际创建 MCP 子进程，完成握手、发现、回测与验证调用，不靠直接 import 函数冒称协议跑通。MCP stdout 留给协议；诊断在 stderr。

## Docker 与 GitHub Actions

Dockerfile 使用 Python 3.13 slim，安装独立依赖，复制研究模块、前端、Skill 与公开样例，以非 root 用户启动。Compose 仅绑定本机 8000，结果保存在 named volume。真实环境变量文件不进入构建上下文。当前机器没有 Docker，我只交付容器定义和 CI 中的 build/run/smoke 检查；没有声称容器已本机运行成功。

GitHub Actions 配置 Windows/Linux × Python 3.11/3.13 的依赖检查、测试和演示研究，并上传产物；另有容器构建、健康接口和核心回测检查。未推送前只能说工作流已写好、尚未远程执行。项目不会替我自动公开发布博客或上传视频，也不会在没有授权时向 GitHub 推送。

## 哪些面试表达是准确的

“我实现了 LangChain 工具封装与可选模型客户端、LangGraph 有界工具循环、FastAPI 后台研究任务和 MCP stdio 服务，提供时点测试与滚动验证。”这是可以从源码检查的事实。

“Agent 自主赚到了钱”“跑赢官方指数”“支持生产级交易”“有分布式断点续跑”都不符合当前实现。人工数据的负收益不妨碍展示工程能力；真实 Alpha 必须另做数据和统计研究。

如果被问“为什么使用 LangChain”，我会回答：统一 typed tools 与模型接口；如果被问“为什么还要 LangGraph”，回答：研究流程有必须执行的节点、共享状态和有界循环；如果被问“MCP 是不是图内工具总线”，回答：当前是独立客户端入口，共享进程内核心，不混淆两条链路。

## 下一步可以做什么

先获得可核验的历史成分和公司行动数据，补正式交易日历、税率分段和更接近真实的成交模型；之后冻结研究协议，留最终 holdout。若服务规模增大，再迁移持久任务队列、取消/超时和独立 worker。新增技术应解决明确需求，而不只是增加简历里的框架名称。
